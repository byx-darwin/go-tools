## 2. 五个重点问题核实结论

1. **Server 端从 metainfo persistent value 读取并校验身份**：✅ 正确无遗漏。JWT（`jwt.go:61-84`）、Session（`session.go:26-36`）、Device（`device.go:28-41`）均通过 `metainfo.GetPersistentValue` 读取，校验顺序合理（先验证有效性再查撤销/存储）。
2. **Client 端通过 `metainfo.WithPersistentValue` 透传身份**：✅ 正确，且优先复用 ctx 中已验证的原始 token/session/device 信息，避免重复签发（`jwt.go:108-119`、`session.go:55-66`、`device.go:60-67`）。三处读写 key 常量统一定义在 `context.go:22-28`，无 key 错配。测试通过 `metainfo.TransferForward` 验证了多跳透传语义（`jwt_test.go:105-108`、`device_test.go:99-108`）。
3. **鉴权失败统一走 `rpcerror.OopsStatusAdapter`**：✅ 完全统一。真实符号 `go-framework/kitex/rpcerror.OopsStatusAdapter`（`rpcerror/error.go:114-136`）。本包所有错误出口（共 12 处）均经过唯一收口函数 `bizError()`（`context.go:82-84`），无散落的自定义错误处理，Recovery 中间件也走同一机制。
4. **改动范围严格限于 `go-framework/kitex/`**：✅ 确认无 hertz 文件改动。核心新增代码 100% 落在 `go-framework/kitex/middleware/auth/`。需注意 diff range 中混入了 `reports/pipeline/pr-98-2026-09-02.md` 等 PR #98 相关文档（疑似分支未从最新 main rebase），建议作者确认这些文件是否应出现在本 PR 中，但不影响本 PR 代码本身的范围判断。
5. **两处 `//nolint` 理由评估**：
   - `jwt_test.go:38`（gocritic ptrToRefParam）：理由清楚（说明是测试输出参数捕获用途），但**可规避**——`noopEndpoint` 若改为接受 `capture func(context.Context)` 回调而非输出指针，可完全消除该 lint 触发点，不需要 nolint。
   - `device_test.go:38`（unparam）：理由是"为未来用例预留 userUUID 参数"，**站不住脚**——实测 4 处调用点（56/66/75/84 行）`userUUID` 实参永远是字面量 `"user-1"`，从未变化，这正是触发 unparam 的原因。"未来可能需要"是推测性理由，不是当前代码库的真实需求。**可规避**：将 `userUUID` 从参数移除、函数体内硬编码，只保留真正会变化的 `deviceID`/`jti`。

综合：两处 nolint 都写明了理由、抑制有效（lint 实测 0 issues），不是滥用，但都存在无需 nolint 的更简洁写法，属于可优化项而非阻塞项。
